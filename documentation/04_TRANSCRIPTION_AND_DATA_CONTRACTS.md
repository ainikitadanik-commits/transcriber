# Файловая транскрибация и контракты данных

Статус: нормативная техническая спецификация
Актуально на: 2026-07-20
JSON schema: 1.3

## Pipeline

### 1. Валидация

- вход существует и является файлом;
- расширение входит в канонический allowlist;
- список частей не пуст;
- части обрабатываются строго в пользовательском порядке;
- модель входит в `v3_e2e_rnnt` или `v3_e2e_ctc`;
- enhancement входит в `auto`, `on`, `off`.

### 2. Нормализация

Каждая часть отдельно преобразуется FFmpeg в:

- codec: `pcm_s16le`;
- channels: `1`;
- sample rate: `16000 Hz`;
- без видеопотока.

В режиме `auto` loudness измеряется через EBU R128. Текущий порог включения
нормализации — ниже `-20 LUFS`. Фильтр при включении:
`highpass=f=70,loudnorm=I=-18:LRA=11:TP=-1.5`.

### 3. Объединение

Нормализованные части объединяются без изменения порядка. Metadata каждой
части хранит собственные границы в общей временной шкале.

### 4. Основное распознавание

- режим GigaAM: `transcribe_longform`;
- batch size UI: `2`;
- RNNT — значение по умолчанию;
- MPS выбирается автоматически, если доступен;
- при `RuntimeError` на MPS вся основная транскрибация повторяется на CPU;
- word timestamps запрашиваются, когда нужна diarization.

### 5. Gap recovery

При включении:

- анализируются интервалы без сегментов длительностью от 3 секунд;
- интервалы без достаточного сигнала пропускаются;
- речь распознаётся окнами до 20 секунд с контекстом 0,75 секунды;
- восстановленные слова ограничиваются core-границами окна;
- итоговые сегменты объединяются и сортируются.

Изменение порогов считается изменением качества pipeline и требует контрольного
аудиосравнения.

### 6. Diarization

- используется локальная модель
  `pyannote/speaker-diarization-community-1`;
- поддерживается optional `num_speakers`;
- результаты называются `Спикер 1`, `Спикер 2`, … в порядке появления;
- имена участников не выводятся;
- при word timestamps фразы группируются с учётом пауз, пунктуации и смены
  спикера.
- near-real-time режим применяет diarization только к системному PCM и сохраняет
  стабильные анонимные метки между окнами по speaker embeddings;
- источник микрофона остаётся отдельной подписью `Микрофон` и не смешивается с
  кластерами участников системного звука.

### 7. Экспорт

Успешная задача атомарно с точки зрения пользователя должна предоставить три
формата: TXT, JSON и DOCX. Частично созданный комплект не считается успешным.

## TXT-контракт

Каждый сегмент:

```text
[HH:MM:SS.mmm --> HH:MM:SS.mmm] Текст сегмента.
```

При diarization:

```text
[HH:MM:SS.mmm --> HH:MM:SS.mmm] Спикер 1: Текст сегмента.
```

Между сегментами — пустая строка. Файл UTF-8 и завершается переводом строки,
если содержит сегменты.

## JSON-контракт 1.3

Верхний уровень:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `schema_version` | string | всегда `1.3` |
| `input` | object | исходник и части |
| `processing` | object | параметры и фактическое выполнение |
| `text` | string | объединённый текст |
| `segments` | array | временные сегменты |

### `input`

- `path`: путь одиночного файла; для multipart — `null`;
- `name`: имя файла или обозначение количества частей;
- `format`: расширение без точки или `multi_part`;
- `size_bytes`: суммарный размер;
- `parts[]`: index, path, name, format, size_bytes, start, end,
  duration_seconds, input_loudness_lufs, enhancement_applied.

### `processing`

- `model`;
- `mode = longform`;
- `device_requested`;
- `device_used`;
- `cpu_fallback_used`;
- `batch_size`;
- `audio`: sample_rate_hz, channels, codec, enhancement_mode,
  enhancement_applied;
- `diarization`: enabled, model, device_used, num_speakers_requested,
  num_speakers;
- `gap_recovery`: enabled, device_used, recovered_segments;
- `started_at`, `completed_at` в ISO 8601;
- `elapsed_seconds`.

### `segments[]`

```json
{
  "start": 0.125,
  "end": 2.5,
  "speaker": null,
  "text": "Добрый день."
}
```

Числа времени округляются до миллисекунд. `speaker` равен `null`, если
diarization не применялась.

## DOCX-контракт

DOCX — человекочитаемое представление того же документа, а не отдельный
источник данных. Он должен:

- содержать метаданные встречи и параметры обработки;
- содержать транскрипцию с таймкодами и спикерами;
- не добавлять факты, которых нет в JSON;
- открываться штатным Word-совместимым ПО;
- создаваться после формирования полного document object.

Точное визуальное оформление MAY улучшаться без повышения JSON schema, если
смысл и полнота не меняются.

## Именование

- одиночный вход: stem исходного файла;
- несколько частей: stem первой части + `-combined`;
- diarization: suffix `-speakers`;
- расширения результата: `.txt`, `.json`, `.docx`.

Изменение схемы именования требует проверки коллизий и обратной совместимости.

## Версионирование

- добавление необязательного поля: повысить minor schema;
- удаление, переименование или изменение смысла поля: повысить major schema;
- потребители должны читать `schema_version`, а не угадывать структуру;
- изменение schema сопровождается примером, тестом и записью в changelog/ADR.
