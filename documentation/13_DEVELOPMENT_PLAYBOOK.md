# Регламент дальнейшей разработки

Статус: обязательный рабочий процесс
Актуально на: 2026-07-20

## Зачем

Этот файл позволяет начать новую задачу с малым контекстом и при этом не
потерять курс. Он не заменяет специализированные документы, а маршрутизирует к
ним.

## Шаг 1. Сформулировать intent

До кода зафиксировать:

```text
Проблема пользователя:
Желаемый результат:
Входит в текущий roadmap:
Не входит в задачу:
Затронутые требования:
Затронутые ADR:
Риск: low / medium / high / critical
Критерии приёмки:
Evidence plan:
```

Если задача не помещается в этот блок, её нужно разделить.

## Шаг 2. Загрузить только нужный контекст

Всегда:

- `00_INDEX_AND_GOVERNANCE.md`;
- этот playbook.

Дополнительно по маршруту из индекса. Не загружать весь репозиторий без
конкретной причины.

Затем проверить только фактические файлы компонента и связанные тесты.

## Шаг 3. Проверить курс

До реализации ответить:

- задача поддерживает текущий этап roadmap?
- не меняет ли она privacy, bundle ID, data path или schema?
- не выдаёт ли planned за current?
- не добавляет ли облако, аккаунт, БД или новую платформу?
- нужен ли ADR?

Если нужен ADR, сначала добавить Proposed decision и критерии выбора.

## Шаг 4. Сделать минимальное изменение

- менять только файлы в scope;
- сохранять существующие контракты;
- не рефакторить соседний код без необходимости;
- не добавлять dependency без обоснования;
- не скрывать неизвестность default-значением;
- пользовательские ошибки писать по-русски и с действием.

## Шаг 5. Проверить

Выбрать уровень из `09_QUALITY_AND_ACCEPTANCE.md`.

Минимум для code change:

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
```

Но тяжёлые pipeline/release/realtime изменения требуют реального smoke или
packaged acceptance.

## Шаг 6. Синхронизировать знание

Обновить только затронутое:

- requirement status;
- специализированную спецификацию;
- ADR;
- open risks/questions;
- changelog/release notes, если это релизное изменение.

Новая подробность кода не обязана попадать в документацию, если она не является
контрактом или решением.

## Шаг 7. Передать evidence bundle

Формат завершения:

```text
Результат:
Изменённые файлы:
Выполненные проверки:
Подтверждённые критерии:
Не проверено:
Открытые риски:
Следующий шаг:
```

## Шаблон handoff в новый чат

```markdown

Канонический контекст:
- documentation/00_INDEX_AND_GOVERNANCE.md
- documentation/...

Текущее подтверждённое состояние: ...
Не считать готовым: ...

Требования: FR-..., NFR-...
ADR: ADR-...
Не входит в scope: ...

Критерии приёмки:
1. ...

Проверки:
- ...

Сначала прочитай перечисленные документы и фактические файлы компонента.
Не меняй продуктовый курс и не закрывай открытые вопросы предположениями.
```

## Checklist перед merge/commit

- [ ] scope не расширен;
- [ ] требования и ADR найдены;
- [ ] privacy-инварианты сохранены;
- [ ] код и документация не противоречат друг другу;
- [ ] тесты добавлены/обновлены;
- [ ] нужный уровень приёмки пройден;
- [ ] planned не назван current;
- [ ] секреты и пользовательские файлы не добавлены;
- [ ] evidence bundle подготовлен.
