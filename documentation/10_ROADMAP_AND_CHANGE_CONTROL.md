# Roadmap и управление изменениями

Статус: зафиксированный порядок развития
Актуально на: 2026-08-12

## Северная звезда

Стабильное локальное macOS-приложение, которое надёжно транскрибирует файлы, а
затем даёт честный near-real-time режим, устанавливается коллегой без
администратора и не передаёт пользовательские данные наружу.

## Правило приоритетов

Порядок важнее количества функций:

1. не ломать privacy и существующую файловую транскрибацию;
2. завершить и принять product `.app`;
3. реализовать near-real-time ASR;
4. закрыть release/signing/legal gaps;
5. только затем расширять продуктовый scope.

## Этап 0. Каноническая документация

Статус: создана этим комплектом.

Результат:

- единый индекс;
- требования с ID;
- архитектура и контракты;
- quality gates;
- ADR и change control.

## Этап 1. Стабилизация `.app`

Статус: реализация есть, полная внешняя приёмка не закрыта.

Цели:

- закрыть privacy-блокер dependency telemetry;
- исправить разрешение встроенных моделей на чистой учётной записи;
- исправить single-instance/port ownership и продуктовый FFmpeg;
- принять ADR-013 через подписанный Core Audio Tap spike на no-admin Mac;
- проверить double-click launch без Terminal;
- проверить menu bar lifecycle;
- принять system audio и microphone prompts без admin credentials;
- подтвердить packaged file transcription;
- синхронизировать README с product `.app`;
- определить установочный UX в `~/Applications`;
- добавить тест/проверку отсутствия второго чужого сервиса на порту 7860.

Выход: внутренняя версия 0.2.x, пригодная для контролируемой эксплуатации.

### Backlog стабилизации

#### BL-001 — Устранить конфликт фиксированного порта 7860

- Приоритет: `P1`.
- Наблюдение: после обновления или некорректного завершения старый
  `transcriber-runtime` может остаться на `127.0.0.1:7860`; новая оболочка
  воспринимает его как чужой процесс и не запускается. Такой же конфликт
  возникает, если порт занят другим локальным приложением.
- Целевое решение: выбирать свободный loopback-порт при запуске, сохранять его
  вместе с `build_id`, `instance_id` и PID в runtime marker и использовать этот
  адрес во всех native/runtime запросах. Старый runtime Транскрибатора можно
  завершать только после строгой проверки product identity; неизвестный процесс
  завершать автоматически запрещено.
- Временный обход: штатно завершить Транскрибатор через меню; если runtime
  остался, остановить пользовательские процессы `Transcriber` и
  `transcriber-runtime`, удалить только `runtime-instance.json` и повторить
  запуск. Пользовательские транскрипции не удаляются.
- Критерии приёмки: запуск при занятом 7860; обновление поверх работающей старой
  версии; очистка stale marker; два последовательных запуска; Quit/restart;
  неизвестный сервис на 7860 остаётся нетронутым; все сценарии проверены в
  packaged `.app`.

UI polish начинается после закрытия privacy, model-resolution, audio-capture
architecture и lifecycle-блокеров. Визуальная доработка не является способом
закрыть недоступный permission flow.

Исключение, одобренное пользователем 2026-07-20: ограниченный visual polish
файлового сценария и честного capture diagnostic разрешён до полного Gate A.
Он не меняет backend/API, не активирует Pause/live ASR/export и не закрывает
ни один product readiness blocker.

## Этап 2. Near-real-time ASR MVP

Статус: следующий крупный функциональный этап.

Порядок:

1. принять ADR об обработке двух источников;
2. собрать benchmark window/overlap на MPS и CPU;
3. реализовать scheduler и state model;
4. реализовать provisional/committed text;
5. реализовать boundary deduplication;
6. обработать временные ошибки;
7. реализовать Stop/finalization/export;
8. пройти 30-минутную приёмку.

Выход: живой текст с измеренной задержкой и финальные файлы без сохранения PCM.

## Этап 3. Release readiness

Статус: зависит от внешних решений.

Цели:

- Developer ID Application;
- hardened signing;
- notarization/stapling;
- чистая Mac/user acceptance;
- юридический правообладатель и условия собственного кода;
- актуальный license bundle;
- документированный update/rollback.

Выход: внешний DMG, который проходит Gatekeeper.

## Этап 4. Качество и эксплуатация

Статус: после стабильного realtime.

Кандидаты:

- постоянный каталог job history;
- безопасная отмена файловой задачи;
- ротация логов и очистка брошенных inputs;
- контрольный аудионабор и метрики;
- более явный health/status экран;
- обновление приложения.

Каждый кандидат требует отдельного scope. Они не должны задерживать realtime,
если не закрывают блокирующий риск.

## Не запланировано

- cloud backend;
- user accounts;
- team workspace;
- automatic participant names;
- Windows/Linux;
- обязательные subtitles;
- public live streaming.

Добавление этих направлений меняет продукт и требует intent review, ADR и
обновления документов 01/02/03.

## Change control

### Обычное изменение

Можно реализовывать напрямую, если оно:

- соответствует текущему вектору;
- не меняет постоянный контракт;
- имеет проверяемые критерии;
- обновляет тесты и затронутую документацию.

### Архитектурное изменение

Сначала ADR, если затронуты:

- сеть или внешние сервисы;
- хранение пользовательских данных;
- bundle identity;
- формат результата;
- model/provider;
- process topology;
- realtime source strategy;
- поддерживаемая платформа;
- install/update path;
- лицензирование.

### Экстренное исправление

Критический bug MAY быть исправлен до полного документационного цикла, но тот
же change set должен:

- описать причину;
- добавить regression test;
- обновить ADR/спецификацию, если фактический контракт изменён;
- не расширять scope под видом исправления.

## Запрет скрытого scope creep

Нельзя добавлять соседнюю функцию только потому, что она «почти бесплатна».
Каждая функция должна отвечать на:

- какую пользовательскую проблему решает;
- входит ли в текущий этап;
- какие требования добавляет;
- какой риск создаёт;
- как будет принята.
